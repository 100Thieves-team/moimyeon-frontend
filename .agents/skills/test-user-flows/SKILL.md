# 핵심 사용자 흐름 테스트

사용자가 제품에서 달성하려는 목표와 관찰 가능한 결과를 중심으로 테스트한다. 테스트 종류보다 실패했을 때 드러나는 사용자 또는 비즈니스 위험을 우선한다.

## 작업 순서

1. 요청, 명세, 수용 기준, 현재 동작과 기존 테스트를 먼저 확인한다.
2. 후보 동작을 `사용자의 행동 또는 입력 -> 관찰 가능한 결과` 형태로 정리한다.
3. 핵심 목표와 명시된 분기, 오류, 경계 조건, 알려진 회귀만 새 테스트 대상으로 선택한다.
4. 공개 인터페이스와 사용자에게 보이는 결과를 검증하는 가장 작은 테스트를 작성한다.
5. 기존 테스트를 보존하고, 요청된 동작 변경으로 기대값이 낡은 경우에만 수정한다.
6. 저장소에서 사용하는 최소 범위의 테스트 명령을 실행한다.
7. 검증한 핵심 동작과 의도적으로 새로 추가하지 않은 비핵심 항목을 보고한다.

## 새 테스트 선택 기준

다음 항목을 우선 포함한다.

- 사용자가 기능을 이용하는 주된 목적과 최종 결과
- 명세나 코드에서 확인되는 중요한 상태, 권한, 데이터, 경로 분기
- 수용 기준에 명시된 검증 오류와 경계 조건
- 실제 장애나 알려진 회귀를 재현하는 사례
- 실패할 경우 핵심 흐름을 막거나 잘못된 비즈니스 결과를 만드는 동작

다음 항목은 명시적인 근거가 없으면 새로 추가하지 않는다.

- 포커스 이동, ARIA 속성, 키보드 조작 같은 접근성 세부 동작
- 픽셀, 색상, 애니메이션, 레이아웃, 특정 뷰포트 크기 같은 시각 세부 동작
- 렌더링 속도나 자원 사용량 같은 성능 세부 동작
- 내부 상태, 비공개 함수, 컴포넌트 구조 같은 구현 세부 동작
- 프레임워크나 외부 라이브러리가 이미 보장하는 동작
- 사용자 결과와 연결되지 않는 단순 렌더링 또는 존재 여부

위 항목도 다음 중 하나가 확인되면 테스트한다.

- 명시적인 수용 기준
- 알려진 회귀 또는 재현 가능한 장애
- 법적 또는 규정상 요구
- 사용자의 직접 요청

## 기존 테스트 보존

- 기존 테스트 파일이나 테스트 케이스를 선제적으로 삭제, 병합, 이동하지 않는다.
- 새 원칙에 맞지 않는 기존 테스트라도 요청된 동작과 충돌하지 않으면 그대로 둔다.
- 동작 변경으로 실패하는 기존 테스트는 삭제하지 말고 새 동작을 반영하도록 기대값을 수정한다.
- 기존 테스트 전체를 정리하는 작업으로 범위를 넓히지 않는다.
- 정책과 맞지 않는 기존 테스트를 발견하면 변경하지 않고 결과에 알린다.

## 테스트 작성 기준

- 테스트 이름에 사용자 행동과 기대 결과를 드러낸다.
- 한 테스트가 하나의 핵심 비즈니스 이유로 실패하도록 구성한다.
- 구현 세부 대신 역할, 입력, URL, 반환값, 화면 상태 등 공개 결과를 검증한다.
- 모킹은 외부 경계를 통제하는 데 필요한 최소 수준으로 제한한다.
- 우연히 포함된 큰 출력이나 DOM 전체를 스냅샷으로 고정하지 않는다.
- 근거가 불명확하면 새 테스트에서 제외하고 그 판단을 보고한다.
